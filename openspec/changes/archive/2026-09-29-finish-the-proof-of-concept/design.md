# Design

## What update detection can honestly claim

OpenSpec records nothing about where an installed schema came from. `schema
fork` and `schema init` write a folder; `schema which` reports only whether it
resolves from the project, the user directory or the package. There is no ref,
no source URL, no hash. This was verified in milestone 01 and is recorded in
`NOTES.md`.

So ossm cannot answer "is this behind?". It can answer "do these files differ
from what the registry offers today?", and those are different questions.

The action is therefore a comparison, not an update check, and it says so. The
message a user sees on a difference names the limitation rather than hiding it:
ossm cannot tell an upstream change from a local edit.

That leaves it useful. Someone who installed a schema and has not touched it
learns that upstream moved. Someone who edited it learns that their copy and the
registry's have drifted. Neither is told something false.

Matching an installed schema to an entry is by `name`, which the registry
explicitly does not make unique. So more than one match is its own answer, and
it names them rather than guessing.

## Comparison is asked for

Comparing fetches. Running it whenever the project view is drawn would turn
opening a tab into a network round trip per schema, on a tool whose whole
offline story is that it does not need one. `u` asks for it, one schema at a
time.

## The acceptance suite is its own file

`test/e2e/acceptance_test.go` holds one case per criterion in the briefing's
section 8, named after the criterion. It is separate from `frame_test.go`
because its audience is different: someone checking whether the proof of concept
does what it promised should be able to read one file.

Where a criterion needs `openspec` or `git`, the case skips with the reason. A
criterion that silently passes because its precondition was missing is worse
than one that visibly did not run.

## The key reference is generated

Every screen already reports its keys through `Keys()`, which is what the help
overlay reads. A `TestMain`-free generator writes `docs/keys.md` from the same
method, and a test asserts the file on disk matches what the code would produce
now. A key reference that drifts is worse than none, and the only way it cannot
drift is if it is not written by hand.

## Demos

VHS tapes in `demo/`, one per thing worth showing, producing GIFs the README
links. They are regenerated by hand rather than by the gate: recording a
terminal takes minutes, and a gate that takes minutes stops being run. The tapes
are checked in, so a stale GIF can be regenerated by anyone.

Each tape drives ossm against a fixture registry and a demo project created by a
script, so recording needs no network and produces the same thing twice.

## The README

What ossm is, what it does, how to run it, and what it cannot do. The last of
those matters most for a proof of concept: someone evaluating it should learn
about the update-detection limit and the git requirement from the README rather
than from a surprise.
